      01 / VORBEREITUNGBestehender LXC

      Ein unprivilegierter Debian-12-LXC (Bookworm) mit installiertem Proxmox Backup Client ist bereits vorbereitet. Debian 12 löste laut bisherigem Setup die Paketprobleme mit libfuse3-3 unter Ubuntu und Debian 13. Die App setzt diese Installation voraus.

      cat /etc/os-release
proxmox-backup-client version

      Falls du den Container neu aufbaust: Debian 12 installieren und den Backup Client nach der offiziellen, zur Distribution passenden Proxmox-Anleitung einrichten.

      Offizielle Installationsanleitung ↗
      02 / DATENQUELLESMB am Proxmox-Host

      Die QNAP-Freigabe wird auf dem Proxmox-Host per SMB/CIFS eingebunden. Der Host reicht sie über die LXC-Konfiguration in den Container durch.

      # Auf dem Proxmox-Host
pct config <CT-ID>
# Beispiel, tatsächlichen Hostpfad verwenden:
mp0: /mnt/qnap,mp=/mnt/Daten,ro=1

      Hostpfad und Container-ID sind Beispiele. Bestehende Mounts beibehalten. Ein schreibgeschützter Mount genügt für Backups.

      03 / PRÜFUNG IM LXCAlle Quellen erreichbar?
      findmnt -T /mnt/Daten/Software
findmnt -T /mnt/Daten/Filme
findmnt -T /mnt/Daten/Serien
findmnt -T /mnt/Daten/Hoerspiele
findmnt -T /mnt/Daten/Musik
findmnt -T /mnt/Daten/Daten

      Die App erwartet CIFS/SMB als Dateisystem, auch bei Durchreichung. Fehlt der Mount, wird der Auftrag abgebrochen. Die Prüfung garantiert nicht, dass eine während des Backups getrennte Freigabe verfügbar bleibt.

      04 / PBS EINRICHTENZugang & erstes Backup

      Dokumentierter Bestand: Datastore pbs1 wurde bereits neu angelegt; das ist kein erneut auszuführender Vorbereitungsschritt. Die CLI-Verbindung über PBS_REPOSITORY und PBS_PASSWORD wurde eingerichtet. Diese Werte bitte separat unter „Backup-Ziele“ übernehmen.

      Der bisherige Software-Testlauf wurde mit --backup-id software gestartet. Die App verwendet ebenfalls diese ID; der erfolgreiche Abschluss und ein Restore sind noch zu bestätigen. Historische CLI-Läufe erscheinen nicht automatisch im lokalen App-Status.

      Unter „Backup-Ziele“ Repository und Passwort oder API-Token-Secret hinterlegen. Der Benutzer benötigt passende Backup-Rechte für den Datastore bzw. Namespace; bei Tokens auch deren eigene Rechte beachten.

      Bei selbst signiertem Zertifikat den verifizierten PBS-Fingerprint eintragen. Danach die gespeicherte Verbindung prüfen und einen Auftrag manuell starten.

      Die Verbindung wird durch eine Snapshot-Abfrage geprüft. Schreibrechte und vollständige Lesbarkeit der Quelldaten werden erst beim Backup überprüft.

      05 / AUTOMATISIERUNGRegelmäßig & nachvollziehbar

      Jeder Ordner erhält eine Uhrzeit und wählbare Wochentage in der eingestellten Zeitzone. Zur Auswahl stehen täglich, werktags, Wochenende, wöchentlich oder eigene Tage; „nur manuell“ deaktiviert den Zeitplan. Zeitpläne laufen nur, solange der Dienst aktiv ist. Verpasste Uhrzeiten werden nicht nachgeholt; bei der Zeitumstellung entfällt gegebenenfalls eine Uhrzeit.

      Pro Ordner wird höchstens einmal je Kalendertag automatisch gestartet. Aufträge laufen seriell. Ergebnisse und letzter Erfolg werden gespeichert; das Protokoll enthält den jüngsten Lauf mit maximal 256 KiB.

      PBS-Aufbewahrung, Prune, Garbage Collection und Verify-Jobs direkt auf dem PBS konfigurieren. Die App löscht keine Sicherungen.

      06 / WIEDERHERSTELLUNGEin Backup ist erst der Anfang

      Im PBS den Snapshot unter host/software (bzw. dem jeweiligen Ordner) auswählen und Dateien testweise herunterladen. Alternativ im LXC in ein separates lokales Testverzeichnis wiederherstellen:

      proxmox-backup-client snapshot list
proxmox-backup-client restore \
  'host/software/<ZEITSTEMPEL>' \
  qnap-software.pxar /tmp/restore-test

      Bei früheren CLI-Snapshots den tatsächlichen Archivnamen im PBS prüfen. Vorher PBS_REPOSITORY, PBS_PASSWORD und bei Bedarf PBS_FINGERPRINT sowie PBS_NAMESPACE in dieser Shell setzen. Die Shell übernimmt keine App-Einstellungen. Niemals zum Test in die produktiven QNAP-Ordner zurückschreiben.

      GOOGLE DRIVE / RCLONEGoogle Drive vollständig einrichten

      Bereits eingerichtet? Direkt Schritt 6 öffnen. Eine zusätzliche, direkt lesbare Dateikopie. Auf dem LXC als root beginnen; Google-Anmeldung und Rclone-Konfiguration gehören zum Dienstbenutzer qnap-backup.

      1 · Rclone im LXC installieren
      apt update && apt install -y rclone
runuser -u qnap-backup -- rclone config --config /var/lib/qnap-backup/rclone.conf

      Bei abweichendem DATA_DIR den Konfigurationspfad entsprechend ändern. Besteht gdrive bereits, mit e bearbeiten; sonst ein neues Remote anlegen.

      2 · Eigene Google-Client-ID erstellen
      1. In der Google Cloud Console ein Projekt anlegen, z. B. QNAP-Backup. Unter „APIs und Dienste → Bibliothek“ die Google Drive API aktivieren.
      2. Unter „Google Auth Platform“ / „OAuth-Zustimmungsbildschirm“ App-Namen und eigene E-Mail eintragen. Für ein privates Google-Konto Zielgruppe Extern wählen und dich als Testnutzer hinzufügen. Unter „Datenzugriff“ den benötigten Drive-Berechtigungsbereich https://www.googleapis.com/auth/drive ergänzen.
      3. Unter „Clients“ / „Anmeldedaten“ einen OAuth-Client vom Typ Desktop-App erstellen. Client-ID und Client-Secret für den nächsten Schritt bereithalten. Die Client-ID endet auf .apps.googleusercontent.com.
      4. Für dauerhafte Zeitpläne unter „Zielgruppe / Audience“ auf In Produktion / App veröffentlichen stellen. Im Testmodus läuft die Freigabe üblicherweise nach sieben Tagen ab. Falls Google Homepage und Datenschutzseite verlangt, diese unter „Branding“ ergänzen. Eine öffentliche Verifizierung ist für eine rein persönliche Nutzung normalerweise nicht nötig.

      Die gemeinsame Rclone-Client-ID wird 2026 abgeschaltet: client_id und client_secret mit deinen eigenen Werten befüllen. Aktuelle Rclone-Anleitung zur Google-Client-ID ↗

      Installation & Grenzen

      Die vollständige Installation als systemd-Dienst steht in der README im Repository. Der Dienst benötigt Leserechte auf den SMB-Ordnern. Die Web-App verwendet ein Passwort-Modal mit Sitzung: Zugriff im vertrauenswürdigen Netz oder über HTTPS-Reverse-Proxy bzw. SSH-Tunnel. Backups werden ohne zusätzliche clientseitige Verschlüsselung erstellt; die Übertragung zum PBS erfolgt über TLS.

      Untergeordnete zusätzliche Mounts werden vom Backup Client standardmäßig übersprungen. Status, Verlauf und letzter App-Erfolg stammen aus Aufträgen dieser App. „PBS-Bestand“ liest zusätzlich vorhandene Snapshots einschließlich früherer CLI-Läufe; das ist keine PBS-Integritätsprüfung.
